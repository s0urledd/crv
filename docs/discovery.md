# Phase 1 discovery

Date: 2026-08-27
Repository: `s0urledd/crv`
Decision: **GO only as a recovery-precondition verifier. Do not use the verdict
word `RECOVERABLE`.**

`crv` can objectively test important prerequisites and can restore a participant
offline far enough to prove that it reaches `SERVING` with its identity intact.
It cannot prove that the node will catch up to the live synchronizer, that an old
physical synchronizer remains usable, or that validator-app and participant
state are semantically consistent. Phase 2 must keep that boundary.

## Evidence convention

Every finding below is labelled with one of the required weights:

- **tested on LocalNet**: reproduced using scripts in `experiments/`; raw,
  redacted output is in `docs/raw/`.
- **from documentation**: supported by a public primary source.
- **reported by operator**: stated in the project brief, not independently
  observed here.

Unknowns are written as **unknown, needs testing**. No production system, key,
token, identities dump, hostname, IP, or party ID was used. The only identities
dump was generated by disposable LocalNet and its secret values are not stored
in this repository.

## Prior art: the pattern to retain

**from documentation.** `restic check --read-data` separates backup creation
from a scheduled read of every stored pack; its docs explicitly recommend
periodic checks and warn that a full read downloads the whole repository.
[`borg check`](https://borgbackup.readthedocs.io/en/latest/usage/check.html)
likewise validates repository and archive consistency independently of backup
creation.

**from documentation.** Velero gives backup and restore distinct phases and
structured warnings/errors. Its restore controller first validates that the
source backup is in a usable phase, and its restore record exposes validation
errors and terminal status. PostgreSQL's
[`pg_verifybackup`](https://www.postgresql.org/docs/current/app-pgverifybackup.html)
uses a capture-time manifest to find missing/extra/corrupt files and WAL, but
the PostgreSQL docs explicitly say this is not a substitute for a test restore.
It also applies to `pg_basebackup`, not the logical `pg_dump` artifacts used by
the documented validator compose procedure. pgBackRest similarly treats
repository verification as its own command.

The extracted product pattern is: a backup artifact is a claim; verification
adds separately recorded, repeatable evidence. A checksum proves bytes, a
restore proves structural usability, and application/network prerequisites
remain separate conditions.

**from documentation.** Adjacent project
[`canton-cro` at `ee0070d`](https://github.com/canton-cro/canton-cro/tree/ee0070deaaa7ecc70b100cd8659e7eebb15d56d7)
orchestrates party/participant recovery. Its evidence bar is a pinned LocalNet
drill, genuine Canton errors, machine-readable state/diagnosis, a safe stop,
and an explicit distinction between real and simulated faults. `crv` must match
that bar and stop before orchestration.

## D1. Backup-set contents and identity

**from documentation.** Splice tells operators to keep both participant
identities and PostgreSQL backups, and the compose example emits one logical
dump for the validator DB and one for the active participant DB. See the
[backup procedure](https://docs.dev.sync.global/validator_operator/validator_backups.html).

**tested on LocalNet.** The quickstart PostgreSQL container contained 11
application databases plus `postgres`; all were owned by `cnadmin`. Relevant
names were `validator-app-provider` and `participant-app-provider`. PostgreSQL
was 14.24. A plain validator dump was 167,984 bytes and took 0.42 s; the
participant dump was 45,577,111 bytes and took 0.80 s. These are bench sizing
observations, not production estimates. [Raw output](raw/d1-backup-shape.txt).

**from documentation.** Production compose naming is version-dependent. Older
deployments select `participant-<migration_id>`. In Splice 0.6.14, `start.sh`
uses `participant` for a new deployment and retains `participant-<id>` only
when `-m` is provided for backward compatibility. The participant DB name is
therefore not safely inferred from the current network migration ID. It must be
read from the deployment's effective `CANTON_PARTICIPANT_POSTGRES_DB` setting.

**tested on LocalNet.** Plain SQL contains source and dumper PostgreSQL versions
and owner statements. It contains neither a reliable source DB name nor any
capture timestamp. A custom-format archive exposes `dbname`, archive creation
time, format, compression, and PostgreSQL versions through `pg_restore -l`.
That archive time still does not prove the ordering rule, because the rule is
“validator backup completed before participant backup started.” Completion time
is not in the archive. File mtime is not evidence of capture time.

**tested on LocalNet.** Neither dump format exposed an exact Splice release.
Flyway/schema versions are compatibility signals, not a one-to-one product
version. Participant identity is intrinsic to a restored participant DB. The
identities dump also contains it directly.

### Metadata provenance

Each item is assigned exactly one provenance class for a specified artifact
form. “Intrinsic after restore” still means the evidence comes only from the
artifact; restoration is the decoder.

| Metadata needed | Class | Finding |
| --- | --- | --- |
| Artifact bytes, size, format | INTRINSIC | Read directly. |
| Current SHA-256 digest | INTRINSIC | A reference digest recorded at capture is still DECLARED. |
| PostgreSQL source/dumper version | INTRINSIC | Present in plain and custom headers. |
| Owner role/schema names | INTRINSIC | Present in logical dump statements/catalog. |
| Source DB name, custom archive | INTRINSIC | `pg_restore -l` exposes `dbname`. |
| Source DB name, plain SQL/PV export | DECLARED | Not present reliably. |
| Archive creation time, custom archive | INTRINSIC | Not authenticated and not completion time. |
| Capture start and completion time | DECLARED | Required to prove strict cross-artifact ordering. |
| Exact Splice/Canton version at capture | DECLARED | Schema versions are not exact releases. |
| Current running Splice/Canton version | DERIVED | Read image tag/version endpoint/workload. |
| Effective participant DB selected at capture | DECLARED | Record the resolved DB, not only `MIGRATION_ID`. |
| Current effective participant DB | DERIVED | Read compose env, participant config, or Helm values. |
| Participant ID/namespace | INTRINSIC | In identities JSON and restored participant DB. |
| Captured physical synchronizer ID | INTRINSIC | Read from restored participant connection state. |
| Current physical synchronizer ID/serial | DERIVED | Participant admin API or Scan. |
| Party hint | DECLARED | Not present in the identities dump. |
| Participant pruning retention at capture | DECLARED | Capture the effective app configuration. |
| Current participant pruning retention | DERIVED | Read effective compose/Helm/app config. |
| Effective network sequencer retention | DECLARED | No public Scan response field exposes it. Use a network-operator source; do not infer it from `~30 days`. |

This result makes the manifest mandatory provenance. Generating a manifest
after the fact may hash files and inspect intrinsic fields, but it must not
invent capture start/completion times from mtime. Missing declared values yield
`UNKNOWN`.

**reported by operator.** The brief says a MainNet compose validator uses
`MIGRATION_ID=4`, `participant-4`, Keycloak, identities export, and six-hourly
`pg_dump`; a TestNet compose validator uses `MIGRATION_ID=1` and Auth0, and was
successfully recovered from `pg_dumpall` after a July 2026 disk loss with party
identity and ingestion offset intact. These are valuable existence evidence,
but the production DB list/owners have not been independently confirmed.
**Unknown, needs testing** with the single read-only command at the end of this
report.

## D2. Ordering and consistency

**from documentation.** The validator backup must complete strictly before the
participant backup begins. This is an explicit requirement in the
[Splice backup procedure](https://docs.dev.sync.global/validator_operator/validator_backups.html),
not a PostgreSQL constraint.

**tested on LocalNet.** At t1, both participant and validator ingestion were at
offset 59. The participant and whole cluster were dumped. A real validator
wallet `tap` then advanced both to 62. The validator app was dumped at t2. The
injected contract ID occurred four times in the t2 validator dump and zero
times in the t1 participant dump. The reversed pair was therefore semantically
different by construction.

**tested on LocalNet.** PostgreSQL restored that reversed pair successfully.
The restored participant remained at 59 while the validator DB recorded 62.
The full restored Canton + Splice stack was started on an internal network;
both services became healthy, the stale reference remained, and no generic
offset/`FAILED_PRECONDITION` error was emitted. [Raw output](raw/d2-ordering.txt).

Conclusion: database restore success and green startup are not proof of pair
consistency. The observable symptom in this controlled experiment was the
known injected contract being present only in the validator artifact. There is
no demonstrated generic query that discovers an arbitrary reversed pair after
the fact. `crv` must enforce documented capture provenance; it must not claim
to infer semantic consistency by starting the apps.

Classification at Phase 1 close: **Recovery prerequisite**. A trusted manifest
can measure it. Missing completion/start times are `UNKNOWN`, not failure and
not pass. The isolated runtime sub-check for “generic semantic consistency” is
**Unverifiable** and does not ship.

## D3. Age and pruning

**from documentation.** The disaster-recovery procedure says a full DB restore
requires a backup less than 30 days old because a participant farther behind
cannot catch up after sequencer pruning. SV pruning docs recommend a one-hour
interval and 30-day retention. Historical participant backups retained for
auditability must be spaced closer than the participant pruning `retention`.

**from documentation.** These are two separate clocks:

1. network sequencer retention limits how old the latest restorable participant
   state may be;
2. participant pruning retention limits spacing if an operator wants continuous
   historical coverage beyond the live DB.

The public Scan `GET /v0/dso-sequencers` schema exposes physical synchronizer
IDs, sequencer URLs, availability time, migration ID or synchronizer serial. It
does not expose `retentionPeriod`. The `~30 days` documentation is authoritative
for the documented policy but is not a live machine-readable network value.
Do not hardcode it. Require a manifest/network-policy input with source and
observed time; absent that, report `UNKNOWN`.

Participant pruning schedule is rendered by the validator Helm chart as
`participant-pruning-schedule { cron, max-duration, retention }`; it is derived
from effective deployment configuration, not reliably from the dump. The safe
maximum historical spacing is strictly less than that configured retention.

Per the corrected gate, this finding was not pre-classified. At Phase 1 close,
the latest-backup age check is **Recovery prerequisite** because the requirement
is explicit and the arithmetic is measurable when both capture completion and
a sourced effective horizon exist. Historical spacing is also a **Recovery
prerequisite**, but only for the separately stated historical-continuity claim;
it must not make the latest backup “not recoverable.” The network behavior was
not simulated. The D7 stale fixture is explicitly arithmetic-only.

## D4. Migration ID and synchronizer identity

**from documentation.** The original thesis needs correction for current
`0.6.x`. Splice 0.6.14 release notes freeze `MIGRATION_ID`; an LSU increments a
new physical synchronizer serial instead. Participant naming and legacy
participant DB names retain the frozen migration ID. LSU replaces the physical
synchronizer while the participant stays tied to the same logical
synchronizer. See the
[release notes](https://github.com/canton-network/splice/blob/398919a5b13479877fd61587003ba7a4ba00091b/docs/src/release_notes.rst#L220-L230)
and [LSU runbook](https://github.com/canton-network/splice/blob/398919a5b13479877fd61587003ba7a4ba00091b/docs/src/sv_operator/sv_logical_synchronizer_upgrade.rst#L20-L58).

**tested on LocalNet.** Starting restored 0.6.11 validator databases with
`MIGRATION_ID=1` did not fail: every app resolved migration ID `0` from stored
offsets and stayed healthy. In a second test, a participant dump was restored
to `participant-0` while the participant was configured to select empty
`participant-1`. The participant health endpoint became green, but the selected
DB had no node identity and `participant.id` reported that the node was not
initialized. [Raw output](raw/d4-migration-and-db-selection.txt).

Conclusion: do not ship the obsolete rule “current migration ID must equal the
number in the participant DB name.” Ship the stronger **Proven invariant**:
the DB selected by the effective deployment must contain the participant ID
declared by the set/identities artifact. Legacy DB naming is useful discovery
evidence, not the invariant.

**from documentation.** A running participant exposes its connected physical
synchronizer ID through `participant.synchronizers.list_connected()`. Scan's
`/v0/dso-sequencers` exposes synchronizer IDs and serial/migration fields;
`/v0/active-synchronizer-serial` exposes the active serial, and `/v0/lsu`
exposes the successor physical synchronizer ID. After an LSU, the logical
synchronizer and frozen migration ID remain; physical ID and serial change.
The old nodes are normally removed after 30 days.

Classification at Phase 1 close: selected-DB identity is **Proven invariant**.
Cross-LSU age plus availability of the captured physical synchronizer is a
**Recovery prerequisite**. Whether old synchronizer nodes are actually usable
may still be `UNKNOWN`; a URL appearing in Scan is evidence of publication,
not an end-to-end catch-up test.

## D5. Isolated verification

**from documentation.** Splice's manual identities procedure explicitly says a
temporary PostgreSQL plus participant is sufficient; the validator app can be
ignored. It suggests `canton.parameters.exit-on-fatal-failures = false` only if
the restored participant shuts down. The docs also state that participant
identities generally cannot be reused on the same global synchronizer.

**tested on LocalNet.** A LocalNet participant dump was restored to PostgreSQL
14 on an internal Docker network. The official participant image reached
`SERVING` in 8.63 seconds, reported zero connected synchronizers, and exposed
the same participant ID as the LocalNet identities dump. The
`exit-on-fatal-failures` override was not needed for this healthy fixture.
The clean reproduction script took 23 seconds end to end. Participant DB size
was 31 MB; observed memory was about 860 MiB for participant and 329 MiB for
PostgreSQL. [Raw output](raw/d5-isolated-restore.txt).

Minimum environment: PostgreSQL plus participant. The validator app is not
needed for structural restore and identity. Adding it did not create a generic
ordering detector in D2. The smallest defensible signal is all of:

- SQL restore completes;
- participant reaches `SERVING`;
- participant ID equals the expected artifact/manifest identity;
- the Docker network is internal and contains no synchronizer service.

An ACS query is not a stronger network recovery proof offline: it shows the
restored local view only. It may be reported as inventory, but is not a
catch-up assertion.

**tested on LocalNet.** Isolation is a safety boundary, not cleanup. A second
copy of the restored participant was deliberately connected to the disposable
source LocalNet while the original existed. With an older fixture its
sequencer subscription hit `PreviousTimestampMismatch`, the synchronizer
fatally disconnected, and the participant exited 117. In two clean reruns with
a small event gap, the duplicate remained connected for the three-minute
observation window. The exact collision symptom is therefore not a dependable
check: duplicate identity is an established safety risk, while immediate
rejection is not an invariant. No public network was involved.

### D5 gate

The isolated test is **Structural validation**. It proves substantially more
than “file parses,” but it cannot prove synchronizer catch-up, ACS agreement
with peers, old-synchronizer availability, or validator/participant semantic
consistency. Therefore `RECOVERABLE` overstates the evidence. Phase 2 proceeds
only under the fallback thesis: recovery-precondition verification plus
optional offline structural restore.

Final aggregate vocabulary proposed for v0.1:

| Verdict | Meaning |
| --- | --- |
| `PRECONDITIONS MET` | Every applicable proven invariant and recovery prerequisite with available evidence passed. This is not a promise that recovery will succeed. |
| `AT RISK` | Required checks passed, but one or more heuristics failed. |
| `PRECONDITIONS FAILED` | A proven invariant or measurable recovery prerequisite failed. |
| `INDETERMINATE` | A required condition could not be established from available evidence. |

Aggregation precedence is `PRECONDITIONS FAILED`, `INDETERMINATE`, `AT RISK`,
then `PRECONDITIONS MET`. Individual checks use `PASS`, `FAIL`, `WARN`, or
`UNKNOWN`.

## D6. Identities dump validation

**from documentation.** The identities endpoint requires an OAuth2 bearer
token with claims accepted by the validator app. The validator deployment docs
require an OIDC provider supporting the client-credentials grant for
machine-to-machine access; provider discovery supplies the token endpoint.
`crv` must accept a token source/config and must not assume Keycloak or Auth0.
A client flow is conceptually:

```text
POST <discovered token_endpoint>
grant_type=client_credentials
client_id=<configured client>
client_secret=<secret from environment/secret store>
audience=<validator API audience, if provider requires it>
scope=<optional provider-specific scope>
```

Do not log the request secret or returned token. The validator call itself is a
read-only `GET /api/validator/v0/admin/participant/identities`.

**tested on LocalNet.** The generated JSON was 2,177 bytes with keys
`authorizedStoreSnapshot`, `id`, `keys`, and `version`; it held three named
base64 key pairs, a decodable topology snapshot, a `PAR` participant ID, and
version `0.6.11`. It did not contain a party hint. [Raw output](raw/d6-identities.txt).

Offline checks can prove JSON/schema/base64 readability, required non-empty
fields, participant namespace shape, and equality with a participant identity
obtained from the DB artifact. Those are **Structural validation**. They cannot
prove a successful re-onboarding.

**from documentation.** Re-onboarding requires the same party hint and a new,
never-used participant identifier, repeated with `-P` on every subsequent
compose start. Parties hosted on multiple participants and external parties are
not migrated automatically. Users onboarded after the DB backup require manual
re-onboarding. Party hint is absent from the identities artifact, and
“never-used” requires external history. These are **Unverifiable** from the
backup set alone and must be reported as explicit `UNKNOWN`/limitations unless
trusted declared or live evidence is supplied.

**unknown, needs testing.** A complete identities re-onboard was not run. It is
inherently a fresh-participant workflow and would cross from structural
verification into recovery orchestration. It does not belong in `crv` v0.1.

## D8. Helm parity

**from documentation.** No cluster was used. Mapping from Splice Helm charts:

| Compose/logical dump check | Kubernetes/Helm equivalent | Gap |
| --- | --- | --- |
| Validator then participant `pg_dump` ordering | Ordered managed-DB backups or PV/CSI snapshots; record provider start/completion/resource IDs in manifest. | Simultaneous or crash-consistent snapshots do not by themselves prove the documented strict order. |
| Dump source DB | `persistence.databaseName`, managed DB instance metadata, or PVC annotation. | Opaque snapshot bytes do not expose a logical DB name. |
| Participant DB selection | Participant chart `persistence.databaseName` plus identity read after isolated restore. | Chart value alone does not prove snapshot contents. |
| Capture time | `VolumeSnapshot.metadata.creationTimestamp` or provider completion time, recorded in manifest. | Kubernetes object time may be lost when only exported storage remains. |
| Splice/Canton version | Deployment/StatefulSet image digest and rendered Helm release values. | Must be captured; current workload version is not the backup version. |
| Participant pruning window | Validator chart `participantPruningSchedule.retention`. | Disabled/omitted schedule must be represented explicitly. |
| Identities file | Kubernetes Secret referenced as participant bootstrap dump. | Secret existence does not validate decrypted JSON; avoid exporting real secret in routine reports. |
| Physical synchronizer identity | Same participant admin/Scan comparison as compose. | Old node usability is still not proven by chart state. |
| Isolated restore | Restore DB/PVC clone into a throwaway namespace with default-deny egress/NetworkPolicy; start participant only. | Needs provider-specific snapshot cloning; **unknown, needs testing** on a real cluster. |

PV snapshots have no equivalent of `pg_restore -l`; provider metadata and the
manifest carry provenance. Isolated verification must clone, never mount or
modify the production PVC.

## Final check classification

Every candidate is assigned exactly one Phase 1 evidence/verdict class. Only
the checks marked “ship” are eligible for v0.1.

| Candidate check | Final class | v0.1 | Verdict effect |
| --- | --- | --- | --- |
| Required artifact path exists (DB pair or identities fallback) | Proven invariant | Ship | Missing all valid paths can fail preconditions. |
| Reference digest/size matches current artifact | Proven invariant | Ship when manifest has reference | Mismatch can fail; no reference is `UNKNOWN`. |
| Selected participant DB identity equals expected participant identity | Proven invariant | Ship | Mismatch/absence can fail. |
| Validator capture completed before participant capture began | Recovery prerequisite | Ship | Trusted reversal can fail; missing provenance is `UNKNOWN`. |
| Latest participant age is below sourced sequencer horizon | Recovery prerequisite | Ship | Measured expiry can fail; unsourced horizon is `UNKNOWN`. |
| Historical backup spacing is below participant retention | Recovery prerequisite | Ship only for declared historical-continuity claim | Failure affects that claim, not immediate latest-set recovery. |
| Backup crossed an LSU and old physical synchronizer remains available | Recovery prerequisite | Ship | Known unavailable old synchronizer can fail; published-but-unproven availability may be `UNKNOWN`. |
| Plain/custom dump parses and SQL restore completes | Structural validation | Ship | Failure can fail artifact path; success never creates a passing verdict alone. |
| Restored participant reaches `SERVING` with expected identity offline | Structural validation | Ship behind isolated mode | Failure can fail artifact path; success does not prove catch-up. |
| Identities JSON fields/base64 are structurally valid | Structural validation | Ship | Failure invalidates identities path; success alone is insufficient. |
| Backup frequency recommendation (for example four hours) | Heuristic | Ship only if operator declares policy | Failure is at most `AT RISK`. |
| Generic validator/participant semantic consistency from offline startup | Unverifiable | Do not ship | D2 showed green startup on a reversed pair. |
| Exact Splice/Canton compatibility inferred from dump schema | Unverifiable | Do not ship | No exact artifact version or proven compatibility matrix. |
| Identities party hint equality from identities JSON alone | Unverifiable | Do not ship as a pass/fail check | Party hint is absent; report `UNKNOWN` unless declared/live evidence supplied. |
| Proposed new participant ID has never been used | Unverifiable | Do not ship | Requires external history and belongs to re-onboarding. |
| Automatic recovery of multi-hosted/external parties and post-backup users | Unverifiable | Do not ship | Report documented limitations. |
